# FloorVault CLI audit — 2026-10-26

Scope: the whole `floorvault` command line at `main` 4cf8abe (after #92):
`floorvault run`, every `floorvault secrets` subcommand, and the inspector's
`floorvault inspect`, plus the CLI claims in README.md, docs/USAGE.md,
SECURITY.md and the hermesvault plugin README.

Method: three independent read-only reviews (one per area) worked from the
rules stated in `agent_cli.py`'s module docstring and the docs, and reproduced
each candidate with real commands against throwaway stores and keys. Each
finding below marked *confirmed* was then reproduced again independently
before it was fixed or recorded. *Suspected* findings come from a code trace
only (most are Windows-specific and could not be run here).

Status: **fixed** = fixed in the PR that adds this report, with a regression
test in `tests/test_cli_audit.py` named after the finding;
**fixed (follow-up)** = fixed afterwards, under tracking issue #101 (see
"Fixed in the follow-up");
**follow-up** = recorded here, not changed; each has its own issue.

## Fixed findings

### RUN-1 — code-loading variable set by a reference
`agent_cli._check_bindings` checked `code_injection_variables(env)` before the
resolved values were added, and `collect()` removes every reference target from
`env`. So `-e LD_PRELOAD=fv:x` (or `NODE_OPTIONS=fv:x`) let a bound item
resolve while a code-loading variable was set.
Reproduced: a bound item resolved with `-e LD_PRELOAD=fv:o`, exit 0; a plain
`LD_PRELOAD` was correctly refused (125).
Fix: the check now includes reference target names.

### RUN-2 — `..` after a symlink
The binding check compared `os.path.abspath(path)` (textual `..` removal), but
`execve` ran the un-normalised path, which the kernel resolves through
symlinks first. With `real/sub -> evil/x/y`, `real/sub/../bin/prog` passed as
`real/bin/prog` and ran `evil/x/bin/prog`. Needs a planted symlink (write
access as the user).
Fix: `run` starts exactly the normalised path it checked.

### RUN-3 — key-file copy with no references
`_prepare_environment` returned before reading the key when the command had no
references, so the copy-stripping never ran.
Reproduced: `COPY=$K floorvault run --key-file k -- sh -c 'echo ${COPY:+present}'`
printed `present`.
Fix: with no references, the key file (if configured) is read only to strip
copies; an unreadable configured key file now fails closed (125). A sealed
credential is still unsealed only when a reference needs it; USAGE.md says so.

### RUN-4 — missing code-injection variables
`UV_PYTHON` lets a configuration choose the interpreter a bound `uvx` runs.
Reproduced with a fake interpreter that logged the bound secret.
Fix: added `UV_PYTHON`, `UV_PYTHON_INSTALL_MIRROR`, `UV_CONFIG_FILE`,
`UV_FIND_LINKS`, `PIP_CONFIG_FILE`, `PIP_FIND_LINKS`.

### RUN-5 — hidden line breaks in env files
`read_env_file` used `str.splitlines()`, which also breaks at `\x0b`, `\x0c`,
`\x1c`–`\x1e`, U+0085, U+2028 and U+2029.
Reproduced: `printf 'GREETING=hello\xe2\x80\xa8STOLEN=fv:o\n'` (one line to
`wc -l`) set `STOLEN` to the secret.
Fix: lines end only at LF, CR or CRLF; a line with any other line-break
character is refused, naming the code point and never the value. Affects
`run --env-file` and `secrets import`.

### RUN-6 — traceback from the command lookup
`Path.exists()` raises for ENAMETOOLONG and EACCES.
Fix: lookup errors map to 127 (126 for a permission error).

### RUN-7 — key copy in the other hex case
`collect()` compared key copies case-sensitively; the key-file path already
used `.lower()`. Fix: both sides lower-cased.

### RUN-8 — `run --help` on stdout
Fix: `run`'s parser prints help to stderr (an MCP client reads stdout as JSON-RPC).

### SEC-1 — `FLOOR_VAULT_KEY_FILE` imported
`_import_plan` refused `CUSTODY_ENV_NAMES` and `APPSTATE_KEY` but not
`KEY_POINTER_ENV_NAMES`. Fix: added.

### SEC-2 — `secrets allow` lost-update
Fix: new `VaultStore.update_allowed_commands(item_id, change)` reads, changes
and writes under one `BEGIN IMMEDIATE` lock; `allow` (add, `--remove`, and the
last-line refusal) runs inside it. A refused change writes nothing.

### SEC-3 — `import --hermes` and `$FLOOR_VAULT_KEY_FILE`
The Hermes path refused `--key-file` (the plugin cannot read key files) but
still read `$FLOOR_VAULT_KEY_FILE`. Reproduced: `--write --remove-from-env`
stored under the file's key and emptied `.env`; Hermes could not open the store.
Fix: `$FLOOR_VAULT_KEY_FILE` is refused there like `--key-file` (exit 2,
nothing stored, `.env` unchanged).

### SEC-4 — key copy imported
Variables were refused by name only, so `VAULT_KEY_BACKUP=<the key>` was
stored and later handed to the child by `run`.
Fix: a value equal (case-insensitively) to a key in sight — the key variables
in the environment and the file, `--key-env`, a key file — is left as is.

### SEC-5 — whitespace-only values
`add_item` drops blank generic fields, but `add` and `import` checked only for
`""`. Fix: `add` refuses a blank value (exit 2); `import` treats it as empty.

### SEC-6 — wrong key on an existing store
`add` opened the store with `create=True` even when it existed, which (a) used
the default provider in key-creating mode and (b) never checked the key.
Reproduced: `add` under a second key exited 0; `secrets list` then failed with
`DecryptionVerificationError` for every user.
Fix: an existing store is opened without key creation, and every `secrets`
command checks that the key authenticates the existing items before acting.

### SEC-7 — field names and pre-prompt validation
Fix: field names must be nameable by a reference (not blank, no leading `:`,
NUL or newline); `put` validates the item id and field before opening the
store or prompting; a blank `put` value exits 2.

### SEC-8 — labels
Fix: `add` refuses labels with control characters (exit 2); `list` escapes
control characters in labels already stored; import labels escape them in the
file name.

### SEC-9 — unresolvable references from `ref`
Fix: `ref` reads the item's field names (never values) and refuses a
multi-field item without `--field`, a field the item lacks, and an empty
`--field`.

### SEC-10, SEC-11, SEC-12
`init --help` no longer shows the key options it refuses; conflicting key
options exit 2; a duplicate `--id` says so.

### INS-1 to INS-7 — `floorvault inspect`
Clean `Error:` lines for corrupt databases (`sqlite3.DatabaseError`),
non-UTF-8 arguments and an empty `--app-instance`; names tried as given, then
ASCII-folded as `EncryptedSQLiteTable` binds them (the output says when the
folded form authenticated); qualified column names refused; an id held by
several rows refused; binary values reported as authenticated (hex with
`--reveal`); new `--id-column` and `--revision`.

## Fixed in the follow-up

Each fix has regression tests in `tests/test_cli_audit.py` (or
`tests/test_agent_cli.py` for SEC-13/14) and curated mutants AUD-6 to AUD-14
in `scripts/mutation_check.py`.

**RUN-10 (medium, Windows).** Confirmed from the CPython source: `shutil.which`
on Windows inserts the current directory before the given path (always on
3.10/3.11; on 3.12+ unless `NeedCurrentDirectoryForExePath` says not to, which
is the default). A `node.exe` in the working directory would have received the
secrets. Fix: on Windows `run` searches only the `PATH` entries, with
`PATHEXT`, skips empty entries (a trailing `;`), and treats a drive-qualified
name (`C:node.exe`) as a path. The search is tested on every platform; the
end-to-end tests run on the Windows CI legs.

**RUN-11 (low, Windows).** Only `KeyboardInterrupt` was handled while waiting;
Python installs no `SIGBREAK` handler, so Ctrl+Break ended `run` and left the
child running. Fix: `SIGBREAK` is ignored from just before the child starts
until it exits, then restored. Tested on the Windows CI legs.

**RUN-12 (low, Windows).** Confirmed from the CPython source, with a narrower
effect than first recorded: Python 3.10 passed both spellings to the child;
3.11+ sorts the environment block and keeps the *last-inserted* of names that
differ only in case. So a later env file that updated the inherited `PATH` in
place lost to an earlier file's `Path=`. Fix: on Windows `collect()` folds
names to upper case as it merges.

**SEC-13.** A Hermes `.env` reached through another spelling (`.ENV` on a
case-insensitive filesystem, or a hard link) was not recognised, so
`secrets import` could rewrite it. Fix: a name other than `.env` counts when
`os.path.samefile` says it is the directory's `.env`; a different `.ENV` file
on a case-sensitive filesystem does not.

**SEC-14.** Reproduced: `import --hermes` chose `--key-env HERMES_VAULT_KEY`
from its own environment only. Hermes loads `<home>/.env` with override before
the plugin runs, so a key set (or cleared) there decides which key Hermes uses.
Fix: the import reads the key from the same view Hermes builds (the
environment with the `.env` loaded over it) and says which one it used.

**SEC-15, #98.** Reproduced: a store created with
`VaultStore(seal_listing_metadata=True)` failed under `run` and every `secrets`
command with "vault listing metadata is sealed". Fix: `open_store` reads the
store's listing mode before any key is used and opens it in that mode;
`secrets seal-listing` converts a store; `--sealed-listing` /
`$FLOOR_VAULT_SEALED_LISTING=1` asserts the mode, so a store turned back to
cleartext is refused. Sealing stays opt-in.

**SEC-17.** Reproduced on Linux with no Secret Service: `secrets add` failed
with the library's disk-fallback refusal and left the store directory
behind. Fix: the provider raises `NoCustodyError`, which the CLI turns into a
hint naming `--key-file` / `$FLOOR_VAULT_KEY_FILE`, `--key-env`, `secrets init
--custody systemd-creds` and the OS extras; the key is resolved before the
store directory is created.

## Follow-ups

**RUN-9 (medium), #97.** `_decrypt_metadata` treats a NULL `allowed_commands`
as "unbound", so anyone who can write `vault.db` can remove a binding without
the key, and an older sealed binding for the same item can be replayed.
Fixing it needs a format change: always store a sealed value (including an
explicit sealed "unbound" marker) and treat NULL as unbound only for rows
written before that change, or bind the binding state into the payload's
authenticated data. Needs a design decision and a SPEC/record-format update.
USAGE.md and the `get_allowed_commands` docstring said a binding "cannot be
edited … undetected"; both now state the limit.

**SEC-16 (suspected), #99.** After `rotate_vault_store`, items are sealed under
a new key generation; the CLI builds a single-key `FloorVault`. Needs `KeyRing`
support in `open_store` before any `secrets rotate` command can exist.

**INS-7 (rest), #100.** `inspect` still has no `--schema-id` /
`--schema-version`.

**INS-8, #100.** `inspect` uses `AdaptiveKeyProvider(service_name)` with no
store directory and no `--key-file`, `--key-env` or sealed-credential support,
so a user whose only key is a key file or a systemd credential cannot use it.

## Documentation mismatches (fixed)

- SECURITY.md and USAGE.md promised that copies of a `--key-file` key never
  reach the child; untrue with no references (RUN-3). Now true; USAGE.md states
  the sealed-credential limit.
- USAGE.md's "Managing items" list omitted `init`.
- USAGE.md's inspect paragraph implied matching custody and context was enough
  (INS-4 to INS-7). Rewritten.
- `secrets init --help` showed options init refuses (SEC-10).
- README.md's Features table had no row for the command line. Added.

## Capability gaps (no CLI command today)

| Library feature | Possible command | Risk to add |
| --- | --- | --- |
| Custody diagnostics (which key source applies and why) | `floorvault secrets doctor` — prints the chosen source and refusal reasons, never creates anything or prints key material | low; the most useful gap given the many refusal paths |
| Ciphertext backup of a store | `secrets backup DEST` (SQLite online backup; key handled separately) | low (ciphertext only); a plaintext export would break "no command prints a value" |
| Freshness anchors (`freshness.py`) | `floorvault freshness verify|init|accept` | medium (`accept` can paper over a rollback); `verify` alone is low |
| Legacy store migration (`migration.py`, `store.py`) | `secrets migrate --dry-run|--write`, `secrets verify` | medium; writes leave residue (SECURITY.md) |
| Master-key recovery bundles (`key_recovery.py`) | `secrets recovery export|restore` | medium–high: key material through files; no-argv handling needed |
| VaultStore key rotation (`vault_rotation.py`) | `secrets rotate --new-key-file … --new-key-id N` | high; needs SEC-16 first or the CLI locks itself out |
| SQLite column migration (`sqlite_migration.py`) | `floorvault migrate-column|verify-column|drop-column` | medium; `drop` is destructive and erasure is not guaranteed |
